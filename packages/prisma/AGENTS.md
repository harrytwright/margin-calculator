# Agents.md (prisma)

Guidance for AI working with Prisma.

**Read [`../../AGENTS.md`](../../AGENTS.md) first.** It covers the conventions that apply across the whole monorepo — 
GitHub PR workflow, signing agent-authored content, conventional commit messages, code-reuse philosophy, 
"never ignore test failures," and the PR-conflict resolution script. This file specializes those rules for 
prisma schema and only add prisma ones

## What this project is

This is our schema store point, since we use separate adaptors as our query builders, one for SQLite and one for 
PostgreSQL, allowing our users the choice of database, one for local work and one for our cloud. 

Our schema is set for postgres. We never use Prisma as an ORM, only as a schama store to generate types

## Relation to adaptors

Each adaptor is a Kysley wrapper, wrapping each required dialect in a way that is compatible with `DatabaseContext` 
from `../shared/src/database/context.ts` allowing us to use the same schema for all adaptors.

Each adaptor handles its own migrations, any change to the schema has to be mirrored by a migration in both adaptors.

## Layout

```text
AGENTS.md
schema/
src/
  types/        -> Auto generated types from the schema
  index.ts      -> Entry point for the schema
  kysely.ts     -> Autogenerated by prisma-kysely
```

You should never edit `kysely.ts` directly, it is autogenerated by prisma-kysely, the same goes with `types/*.ts`, this 
is generated by `./scripts/generate.js` and is run on every build as `postbuild` script.

## Prisma Schema

The schema is multi-filed; each main table should have its own file, which should include any related joining 
tables, enums, or views. Any shared enums should be defined in the `./schema/shared.prisma` file. The entrypoint is 
`schema.prisma` this should only store generators, `datasource` without a URL, as Kysely is our query-builder

## Changes

Any work done here should be done in a PR against the `main` or current `PR` branch. This is to avoid conflict, as 
changes here can affect multiple packages. 

Changes should be done incrementally where possible, if you are doing a minor schema change this is fine, 
flow of changes should be as follows:

1. `@menubook/prisma`: Adjust schema, editing existing tables or adding new ones
2. `@menubook/{sqlite|postgres}`: Create a mirrored migration in both adaptors for the change
3. `@menubook/core`: Update any query changes to the database services within `../core/src/services/*.ts`. These are 
    CRUD-like methods.
4. `@menubook/{cli,app}`: Update any types where needed, changes to the above packages will have to be reflected here.
